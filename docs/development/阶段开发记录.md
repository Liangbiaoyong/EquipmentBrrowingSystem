## 三、模块1：用户认证与权限基础

### 3.1 CAS 认证流程（最终实现方案）

不走标准 CAS Client 协议（CAS 2.0/3.0），采用 **Token 代理模式**：

```
浏览器 → 跳转 CAS 登录 (newcas.gzhu.edu.cn)
     → CAS 回调返回 token
     → POST /api/v1/auth/cas/login {token, cookies}
     → 后端调 https://libbooking.gzhu.edu.cn/ic-web/auth/userInfo 验证
     → 解析 JSON，提取用户身份
     → 首次登录自动建用户，重复登录更新信息
     → 签发自有 JWT 返回
```

**选择 Token 代理模式的理由**（基于 TEMP 目录的 CAS 实现分析）：

- 广州大学 CAS 通过图书馆认证中心中转，不是标准 CAS 协议
- crypto 加密方式（des.js 的 strEnc）在 Java 中缺乏直接等价实现
- Token 代理模式零依赖 CAS 客户端库，运维简单

### 3.2 学生/教师识别规则

| 判断方法                      | 学生                       | 教师               |
| ----------------------------- | -------------------------- | ------------------ |
| `ident` 字段                | `257`                    | `259`            |
| `deptName` vs `className` | 不一致（学院名 ≠ 班级名） | 一致（均为学院名） |

代码中优先以 `ident` 字段为准。

### 3.3 数据库关键设计

`sys_user` 表新增 10 个 CAS 专属字段：

```
cas_uuid      → CAS 系统全局唯一 UUID
acc_no        → CAS 账号编号
class_name    → 班级名称
class_id      → 班级 ID
dept_id       → 学院/部门 ID
ident         → 身份标识（257=学生，259=教师）
card_no       → 一卡通号
sex           → 性别
expired_date  → 账号过期日期
last_cas_login→ 最近 CAS 登录时间
```

**设计原则**：

- `auth_source='C'`（CAS）的账户 password 为空，不从密码登录
- `auth_source='L'`（Local）的账户走 BCrypt 密码验证
- 实验室管理员通过手动提升 userType 实现，不会被后续 CAS 登录降级

### 3.4 JWT 安全模型

```
Token 结构：
  Header:  { "alg": "HS512" }
  Payload: {
    "sub":     "用户ID",
    "username": "登录名",
    "roles":    ["ROLE_STUDENT", ...],
    "userType": 0,
    "iat":      签发时间,
    "exp":      过期时间（+4h）
  }
  Signature: HMAC-SHA512(header.payload, secretKey)

Principal: JwtUserPrincipal { userId, username, userType, roles, authorities }
Credentials: null（不存储原始JWT，防止日志泄露）
```

### 4.2 自动分类算法

```
输入: 国标分类名（如 "其他照相机及器材"）

Step 1: 预处理
  original    = "其他照相机及器材"
  normalized  = "照相机及器材"     // 去掉前缀"其他"

Step 2: 规则遍历（按 priority ASC）
  规则表:
    priority=50:   "照相机" → category_id=2 (摄影摄像)
    priority=100:  "计算机" → category_id=1 (计算机及外设)
    ...

Step 3: 首次包含匹配命中即返回
  规则 "照相机" 匹配 "照相机及器材" ✅
  → 返回 category_id = 2

Step 4: 全未命中
  → 返回 null → 调用方归入 category_id=10 (其他设备)
```

**设计要点**：

- 优先级机制：精确匹配词（如"无人机"priority=50）优先于泛匹配词（如"仪器"priority=100）
- 预处理去"其他"："其他照相机及器材"→"照相机及器材"，命中"照相机"关键词
- 兜底归入"其他设备"：无法分类的自动归入 category_id=10
- 管理员可增删改规则，无需重启服务

### 4.4 CSV/XLSX 格式要求

| 格式 | 编码/要求                      | 解析方式           |
| ---- | ------------------------------ | ------------------ |
| CSV  | UTF-8 编码，逗号分隔，引号转义 | 自定义状态机解析器 |
| XLSX | Excel 2007+                    | Apache POI 5.2.5   |

**关键解析能力**：

- 金额字段（含千分位逗号如 `"17,500"`）→ BigDecimal
- 日期字段：自动识别 Excel 序列号（如 `46182`）和文本日期（如 `2026-03-15`）
- 空值安全：null 字段不入库，保留数据库默认值

### 4.5 导入去重策略

```
按 asset_no 查找已有记录:
  存在 → UPDATE（更新所有字段，保留原 id）
  不存在 → INSERT（新建记录）

并发安全：
  INSERT 失败 (DuplicateKeyException) → 重新 SELECT → UPDATE
```

## 五、模块3：借用审批与权限体系

### 5.1 权限体系设计

采用 `module:action` 细粒度命名，16 个权限标识。用户类型 → 权限列表由 `PermissionConstants` 集中映射：

| 用户类型         | 权限数 | 典型权限                                                                                     |
| ---------------- | :----: | -------------------------------------------------------------------------------------------- |
| STUDENT (0)      |   8   | `device:view` `borrow:create` `borrow:my` `borrow:return`                            |
| TEACHER (1)      |   10   | 学生全部 +`approval:first` `statistics:view`                                             |
| LAB_ADMIN (2)    |   12   | `device:manage` `approval:first` `approval:second` `return:manage` `repair:manage` |
| SYSTEM_ADMIN (3) |   16   | 全部权限 +`admin:user` `admin:config` `admin:log` `admin:backup`                     |

权限在 `JwtAuthenticationFilter` 中自动注入到 `Authentication.authorities`，Controller 用 `@PreAuthorize("hasAuthority('device:manage')")` 做方法级拦截。

### 5.2 借用申请与冲突检测

```
POST /api/v1/borrows
{
  "deviceId": 1,
  "startTime": "2026-07-10T09:00:00",
  "endTime": "2026-07-10T17:00:00",
  "reason": "课程设计需要",
  "approverId": 5   // 指定审批人（教师）
}
```

冲突检测算法：查询同一设备在目标时段内是否存在以下状态的借用 →

- `PENDING_APPROVAL` / `APPROVED` / `BORROWING` / `OVERDUE`

### 5.3 审批流程引擎

默认二级审批，审批流定义以 JSON 快照存入 `borrow_record.approve_flow_def`：

```
申请人提交 → 指定审批人（教师）= 一级
           → 通过 → 实验室管理员 = 二级
                  → 通过 → APPROVED（库存-1）
           → 任一驳回 → REJECTED（终止）
```

**admin 特殊处理**：系统管理员（userType=3）拥有 `approval:first` 和 `approval:second`，可处理任一级审批。实验室管理员（userType=2）通过额外注入 `approval:first` 也可处理一级。

### 5.4 归还管理

- 归还登记：记录实际归还时间 + 设备状况描述
- 逾期自动计算：`Duration.between(endTime, now).toDays()`
- 库存恢复：`available_qty + 1`
- 损坏处理：有 `damageReport` → 设备标记「维修中」

### 5.5 设备图片管理

| 功能     | 说明                                                                |
| -------- | ------------------------------------------------------------------- |
| 添加图片 | `POST /devices/{id}/images?imageUrl=...` → 无封面时自动设为封面  |
| 删除图片 | `DELETE /devices/images/{id}` → 删除封面图自动用下一张替代       |
| 缺图查询 | `GET /devices/missing-images` → 查询无图片的设备（用于管理整改） |

### 5.6 统计与系统管理

- **仪表盘** `GET /statistics/overview`：设备总数/可借用/借用中/维修中/待报废 + 借出/逾期/待审批数量
- **用户管理** `GET/POST/PUT /admin/users`：列表/创建/角色变更/启用禁用

## 六、模块4：设备详情增强 + 借用时长限制 + 系统配置管理

### 6.1 需求细化过程

原始需求：设备可以借用。实际细化后：

- **借用时长**：最大1周（7天），任何时间段均可（不限于工作时间）
- **时长限制必须可配置**：不能硬编码，Admin 后台可运行时修改，无需重启
- **设备详情**：不能只返回裸设备字段，必须展示图片、当前借用状态、历史借用次数

### 6.2 借用时长限制（双源配置）

```
优先级：数据库 system_config 表 > application.yml 默认值

提交借用时：
  1. configService.getIntValue("borrow.max_days", 7)  → 读取有效期上限
  2. ChronoUnit.DAYS.between(start, end)              → 计算借用天数
  3. borrowDays > maxDays → 拒绝并提示"最多 X 天"
```

配置修改方式：

- **application.yml**：`borrow.max-days: 7`（默认值，部署时设定）
- **Admin API**：`PUT /admin/config/borrow.max_days?value=14`（运行时修改，即时生效）
- **Admin API**：`DELETE /admin/config/borrow.max_days`（恢复默认值）

### 6.3 系统配置表设计

```sql
system_config (
  id           bigint PK,
  config_key   varchar(100) UNIQUE,   -- borrow.max_days
  config_value varchar(500),          -- 7
  description  varchar(200)           -- 借用最大天数
)
```

**优先级逻辑**（SystemConfigServiceImpl）：

1. `SELECT config_value FROM system_config WHERE config_key = ?`
2. 有值 → 返回数据库值
3. 无值 → 返回 `defaultValue`（来自 `@Value("${borrow.max-days:7}")`）

### 6.4 设备详情 DeviceDetailVO

```
GET /api/v1/devices/{id}  → 返回：
{
  "device":           { 设备基本信息 },
  "images":           [ 图片列表（已排序） ],
  "categoryName":     "计算机及外设",
  "isBorrowing":      true/false,
  "currentBorrower":  "用户ID:5",
  "expectedReturnTime":"2026-07-14T17:00:00",

```

查询逻辑：

- `borrow_record` 表查当前 BORROWING/OVERDUE 状态（`isBorrowing`）
- `borrow_record` 表 COUNT 获取历史借用次数

## 七、模块5：运维安全与通知体系

### 7.1 定时清理策略

每天凌晨3点执行（`@Scheduled(cron = "0 0 3 * * ?")`），分为四类操作：

| 清理项                         |    保留周期    | 配置键                        | 可运行时修改 |
| ------------------------------ | :------------: | ----------------------------- | :----------: |
| 通知(notification)             | **15天** | `cleanup.small_record_days` |      ✅      |
| 操作日志(sys_log)              | **15天** | `cleanup.small_record_days` |      ✅      |
| 审批记录(approval_log，已完成) | **15天** | `cleanup.small_record_days` |      ✅      |
| 附件/借用归还图片(attachment)  | **30天** | `cleanup.large_file_days`   |      ✅      |

**注意**：借用单(borrow_record)本身及其 approve_flow_def JSON 快照**永久保留**，不做清理。

额外执行：

- 逾期检测：BORROWING 且 endTime < now → 标记 OVERDUE + 通知
- 归还提醒：明天到期的借用 → 提前通知借用人

### 7.2 登录频率限制

Redis 滑动窗口实现：

- 每 IP 每分钟最多 **5 次**登录尝试
- 超限后锁定 **5 分钟**
- 登录成功自动清除计数

### 7.3 Token 黑名单

```
POST /auth/logout → Token 加入 Redis 黑名单（有效期=Token剩余时间）
JwtAuthenticationFilter → 每次请求先查黑名单 → 命中则拒绝
```

用途：登出后Token立即失效、管理员修改角色后废掉旧Token。

### 7.4 操作日志审计

AOP 切面自动拦截所有 `@PostMapping`/`@PutMapping`/`@DeleteMapping` 方法：

- 记录：用户ID、用户名、方法签名、参数（截断500字符）、IP、耗时、成功/失败
- 查询：`GET /admin/logs?username=&status=`（仅 SYSTEM_ADMIN）

### 7.5 当前系统配置项

| 配置键                            | 默认值 | 说明           |
| --------------------------------- | :----: | -------------- |
| `borrow.max_days`               |   7   | 借用最大天数   |
| `borrow.default_approval_steps` |   2   | 默认审批级数   |
| `cleanup.small_record_days`     |   15   | 小记录保留天数（日志/审批记录） |
| `cleanup.large_file_days`       |   30   | 大文件保留天数 |
| `notification.read_cleanup_days` |  180  | 已读消息保留天数（默认半年） |
| `notification.unread_cleanup_days` | -1  | 未读消息保留天数（-1=永久） |

## 九、开发规范（从实际开发中沉淀）

### 9.1 代码规范

- 所有 API 返回统一使用 `R<T>` 封装，错误走异常而非手动构造失败响应
- Controller 只做参数校验+路由，业务逻辑全部在 Service
- 私有辅助方法需有清晰 JavaDoc，公开方法有 `@ApiOperation`
- 字段映射使用 MyBatis-Plus 的 `map-underscore-to-camel-case: true`
- 时间字段统一用 `LocalDateTime` / `LocalDate`，不使用 `Date`

### 9.2 安全规范

- 认证过滤器不存储原始 JWT 到 credentials（防日志泄露）
- Principal 使用自定义 `JwtUserPrincipal` 而非裸 Long
- `/actuator/**` 仅公开 `/actuator/health`，其余需认证
- 密钥注入用 `@Value`，长度不足 64 字节启动报错
- 登录端点 Redis 滑动窗口频率限制（5次/分钟→锁定5分钟）
- 登出 Token 立即失效（Redis 黑名单）
- 密码最低 8 位，用户名最低 3 字符

### 9.3 测试规范

- 每个 Service 至少覆盖：正常路径、异常抛出、边界条件
- 不依赖 `Thread.sleep` 测试超时（用 0ms 过期 token）
- Controller 测试不满足于 `status().isOk()`，必须验证 JSON 响应体
- Mock 使用：Service 层 `@Mock`；Controller 层 `@MockBean`
- 避免测试私有方法通过反射调用（耦合实现细节）

### 9.4 提交规范

- 每完成阶段性成果后自动 git add + commit + push
- 提交类型前缀：`feat` / `fix` / `docs` / `refactor` / `test` / `chore`
- 测试 + 代码审查通过后方可提交
- 提交前必需 `mvn test` 全通过

## 十二、V2.2：批量导入修复 + 智能导入（2026-07-11）

### 12.1 问题分析

**Bug 1：CSV仅导入20行（应有2000+行）**
- 根因：中文Windows Excel导出的CSV为**GBK编码**，但代码使用UTF-8读取
- GBK中文在多字节UTF-8解码时产生乱码及不可预期的字符
- 导致BufferedReader行读取在部分行提前中断

**Bug 2：XLSX导入返回0行**
- 根因：学校系统导出的文件可能是旧格式 `.xls`（HSSF），但代码仅处理 `.xlsx`（XSSF）
- `XSSFWorkbook` 无法读取 `.xls` 格式 → 静默失败返回0行

**Bug 3：数据乱码**
- CSV文件为GBK编码但按UTF-8解码 → 中文字段在数据库中显示为乱码
- 由于 `application-dev.yml` 中 `spring.servlet.encoding.charset=UTF-8` 强制UTF-8，需要导入服务自行处理编码

### 12.2 修复方案：编码自动检测

```
CSV编码检测流程：
1. 读取文件全部字节到内存
2. 检查BOM头 (0xEF 0xBB 0xBF) → UTF-8-BOM
3. 否则尝试UTF-8解码 → 验证表头是否含"资产编号"
   - 表头正常 → UTF-8
4. 否则 → GBK解码
```

### 12.3 Excel格式兼容

同时支持 `XSSFWorkbook`（.xlsx）和 `HSSFWorkbook`（.xls）：
- 首先尝试 `new XSSFWorkbook(bytes)` 
- 失败则回退 `new HSSFWorkbook(bytes)`
- 两者都失败则返回错误信息

### 12.4 智能导入策略（核心功能）

以 `asset_no`（资产编号）为主键，三步完成：

```
第一步：扫描新文件
  └→ 收集所有 asset_no 到 Set<String> newAssetNos

第二步：删除旧数据（增量同步）
  └→ 查询数据库所有 asset_no
  └→ 不在 newAssetNos 中的 → DELETE
  
第三步：逐行 Upsert
  └→ asset_no 已存在 → UPDATE（更新业务字段，保留关联数据）
  └→ asset_no 不存在 → INSERT（缺失值使用默认值）
```

**保留的关联数据**（更新时不被覆盖）：
- `borrowType`（借用类型，手动设置）
- `laboratoryId`（所属实验室，手动设置）
- `coverImage`（封面图）
- `description`（备注，仅在新数据无描述时保留旧值）
- `defaultApproverId`（默认审批人）
- 关联的 `device_image` 图片列表

**新增记录的默认值**：
- `borrowType` = 2（可借出）
- `status` = 1（可借用）
- `totalQty` = 从文件读取，默认1
- `availableQty` = 同 totalQty

### 12.5 新增响应字段

`ImportResultDTO` 新增 `deleteCount` 字段，返回被删除的旧记录数：

```json
{
  "totalRows": 2469,
  "successCount": 500,
  "updateCount": 1969,
  "deleteCount": 150,    // V2新增：删除的旧记录数
  "failCount": 0,
  "autoCategoryCount": 2300,
  "uncategorizedCount": 169,
  "batchId": "a1b2c3d4"
}
```

### 12.6 技术要点

- 将 CSV 全部内容读入内存后处理，避免流式读取时的编码问题
- 使用 `StringReader` + `BufferedReader` 逐行解析（编码已在读入时解决）
- 批量写入仍保持 `BATCH_SIZE=200` 的流式提交
- 新增方法上的 `@Transactional` 确保删除+更新+插入的原子性

## 13. V2.3 逾期管理口径统一与读取时推导

## 14. V2.4 全链路时区统一 + 设备介绍（2026-09-29）

### 14.1 时区问题与根因

现象：界面与日志的时间比北京时间慢 8 小时。

实测根因是**整个系统跑在 UTC**，而只有一层被单独配置过：

| 层 | 实测值 |
| --- | --- |
| 宿主机 `timedatectl` | `Local time: ... UTC` |
| `dev-backend` 容器 `date` / `TZ` | UTC / 空 |
| `dev-mysql` 容器 `@@global.time_zone` / `NOW()` | `SYSTEM` / UTC |
| `application-*.yml` `spring.jackson.time-zone` | `Asia/Shanghai`（**只有这一层是对的**） |

所以同一时刻后端日志打 `09:38`、而 Spring 错误 JSON 打 `17:38`——Jackson 只负责把 `Date`/`Instant` 转换时区，**日志时间戳和 `LocalDateTime` 都不经它**。

关键认知：**`LocalDateTime` 不参与任何时区换算**。JVM 在 UTC 下 `LocalDateTime.now()` 返回的是 UTC 墙钟，直接写库、直接序列化、前端原样显示，于是全链路偏 8 小时。

### 14.2 四层对齐

| 层 | 改动 | 作用 |
| --- | --- | --- |
| 容器 | `docker-compose.yml` 五个服务统一 `TZ: Asia/Shanghai` | 容器内 `date`、进程默认时区 |
| MySQL | mysql 服务加 `--default-time-zone=+08:00` | `NOW()`/`CURRENT_TIMESTAMP` 及 datetime 列默认值 |
| JVM | `backend/Dockerfile` 加 `ENV TZ` + `apk add tzdata` + `-Duser.timezone=Asia/Shanghai` | `LocalDateTime.now()` 与**日志时间戳**；TZ 与 JVM 参数双保险 |
| 前端 | 新增 `src/utils/datetime.js` | 提交给后端的时间不再用 UTC |

`frontend/Dockerfile` 也加了 `ENV TZ`，保证 nginx 日志时间戳一致。

### 14.3 存量数据平移（一次性）

V14 之前所有 datetime 列写入的都是 UTC 墙钟，需整体 +8 小时。脚本：`sql/migrations/16-timezone-cst-shift.sql`。

- **放在 `sql/migrations/` 而非 `sql/init/`**：`sql/init/` 是全新数据库的初始化目录，新库的数据本来就是北京时间，再 +8 会污染。放外面靠手工执行。
- 覆盖 17 张表、34 个 datetime 列；`DATE_ADD(NULL,...)` 仍为 NULL，无需判空。
- 幂等：以 `system_config.db.timezone_shifted` 为标记，重复执行不会二次平移。
- 易错点：`create_time`/`update_time` 带 `ON UPDATE CURRENT_TIMESTAMP`，凡有该列的表都在同一条 UPDATE 里显式赋值，否则会被自动刷成 `NOW()`。

### 14.4 前端 UTC 修正

`new Date().toISOString()` 按 UTC 输出，凡是要提交给后端或做日期判断的地方都改掉：

| 位置 | 原问题 |
| --- | --- |
| `BorrowCreate.vue`（两处） | 现场借用把 `startTime` 写成 UTC 墙钟、`endTime` 写成「UTC+8h」，实际造出一个 8 小时窗口，与界面「自动设为当天」的约定不符。改为 `todayRange()` 取当天 00:00:00 ~ 23:59:59 |
| `MyBorrows.vue` | 取走回填 `pickupTime` 用 UTC |
| 6 个导出点 | 文件名日期在 UTC 与本地跨天时会差一天 |

### 14.5 设备介绍

设备详情页底部新增「设备介绍」区块，介绍设备功能与可完成的实验。

- **复用既有 `device.description` 字段**，不新增表/列——该字段此前从未在任何界面出现。
- 编辑权限由服务端判定并随详情返回 `canEditIntro`，前端据此显示入口：**实验室管理员 / 系统管理员 / 该设备登记的使用人本人**。
- 复用既有 `PUT /devices/{id}`，其鉴权与字段限制已吻合：教师（`userType=1`）在该接口内被限制为「仅本人名下设备」且可改 `description`。前端只提交 `{description}` 一个字段，MyBatis-Plus 的 `updateById` 忽略 null，不会误改其它列。
- **客户端角色状态不可靠**：原先 `DeviceDetail.vue` 读的 `localStorage.getItem('userType')` 从未被写入过，`isAdmin` 实际只靠 `device:manage`。故本次权限判定放在服务端，不在前端重建一套。
- 限制：判定沿用既有规则，仅覆盖 `userType=1`（教师）作使用人的情形；若某台设备的使用人是学生账号，其无 `device:manage`，无法编辑。

## 16. V2.6 时区迁移的过度平移修正（2026-09-29）

### 16.1 问题

V2.4 的时区同步上线后，历史数据平移脚本 `16-timezone-cst-shift.sql` **按「全库都是 UTC 墙钟」一刀切**，
把 `borrow_record` 的 `start_time`/`end_time`/`real_return_time`/`outcome_recorded_time`/`create_time`
以及 `approval_log.operate_time` 也 +8 小时。**这些列本来就是正确的本地时间**：

`sql/init/03-test-data.sql` 中它们由**字面量**推导而来，不是 `NOW()`：

| 列 | 来源 |
| --- | --- |
| `start_time` | 第 65 行 `CONCAT(@day,' ',@start_hour,':00:00')` |
| `end_time` | 第 66 行 `@start_time + N 天` |
| `real_return_time` | 第 117/118 行 `@end_time + N 天` |
| `outcome_recorded_time` | 第 131 行 `@end_time + N 天` |
| `create_time` | 第 132 行 `@start_time - N 天` |
| `approval_log.operate_time` | 第 147/152 行 `@start_time - 1 天` |

**根因**：误把「所有 datetime 列都来自系统时钟」当成前提。实际上时间列的来源分两类——
一类是**用户选择/脚本字面量**（前端日期选择器 `value-format="YYYY-MM-DDTHH:mm:ss"` 输出的是本地墙钟，
后端原样落库，从不经过 UTC），另一类是**系统生成**（`NOW()`、`CURRENT_TIMESTAMP`、`LocalDateTime.now()`）。
只有后者需要平移。

实测影响：1840 条借用记录中 **1786 条**（种子行）的上述列被推快 8 小时。

### 16.2 判别种子行

`update_time` 在种子里是灌数据时刻的 `NOW()`，因此高度聚集（实测两个批次：
`2026-08-26 22:11:0x` 共 1599 行、`2026-07-13 15:39:2x` 共 187 行）。
而种子行的 `create_time` 由整点字面量推导、秒恒为 0。故：

```sql
SECOND(create_time) = 0 AND create_time <> update_time
```

可稳定识别种子行（1786 行），其余 54 行为应用创建。

### 16.3 修正

新增 `sql/migrations/17-timezone-fix-authored-columns.sql`（已在生产库执行）：

| 列 | 处理 |

## 17. V2.7 逾期管理三处缺陷 + 归还审批字段透传（2026-09-29）

### 17.1 逾期统计全为 0 / 接口 500 —— 表根本不存在

**现象**：逾期管理页四张统计卡片全是 0，而下方列表正常有数据；同时弹出「服务器内部错误」。

**根因**：`overdue_record` 表在部署库里**不存在**。

```
Caused by: java.sql.SQLSyntaxErrorException: Table 'device_borrow.overdue_record' doesn't exist
```

该表由 `sql/init/08-update-v6-overdue.sql` 创建，但 `sql/init/` 挂载到 `/docker-entrypoint-initdb.d`，
**只在数据库首次初始化（数据目录为空）时执行一次**。这个文件是在卷已存在之后才加入仓库的，
因此从未执行。`overdueStats()` 用它统计「催还中/已强制归还」，一查就抛异常 → 500 →
前端 `catch` 后统计停在默认值 0。

> 统计卡片与列表用的是**同一个** `overdueCondition()`，所以「列表有数据、统计为 0」本身就是
> 「接口报错」而非「口径不一致」的信号。

**处理**：新增 `sql/migrations/18-create-overdue-record.sql` 补建该表（幂等）。线上库已执行。
另：线上库共缺这一张表，已与 `sql/` 中定义的 18 张表逐一比对确认。

**顺带修复**：`sql/init/12-update-v10-overdue-enhanced.sql` 整份内容已被 08 号脚本覆盖
（只多一个实体中并不存在的 `fine_paid`），且它使用的
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` **是 MariaDB 语法，MySQL 8 不支持**，
在全新初始化时会直接报错并中断后续脚本。已删除该文件。

### 17.2 超过结束时间却仍显示「借用中」

**根因**：借用单的状态列只由定时任务更新，原 cron 为**每天 03:00 一次**。于是：

- 记录刚过期 → 到下次执行前，列表（读 status 列）显示「借用中」，
  而统计（读取时推导 `end_time < now`）已计入逾期 —— 两者必然不一致；
- `@Scheduled` **对错过的执行不做补偿**，服务器若恰在 03:00 前后重启，当天就整天空过。

**处理**：把逾期检测从每日清理任务中抽出为独立方法 `markOverdue()`：

| 触发方式 | 说明 |
| --- | --- |
| `@Scheduled(cron = "0 0 * * * ?")` | 每小时执行，滞后窗口从 24h 缩到 1h |
| `@EventListener(ApplicationReadyEvent)` | 启动时补跑一次，部署后立即可见、也能自愈停机期间的积压 |

方法幂等（只取 `status='BORROWING'` 的记录），重复执行不会重复通知。

### 17.3 逾期管理移除「强制归还」

「强制归还」与「归还」功能赘余，按要求只保留「归还」：

> 后端 `PUT /borrows/{id}/force-return` 端点保留未动（本次只改页面）。

### 17.4 归还审批看不到学生填写的「设备情况」

## 18. V2.8 设备详情、借用浏览导出、统计口径与权限（2026-09-29）

### 18.1 设备详情「当前借用人」永不显示

`DeviceDetailVO` 里是 `private boolean isBorrowing;`。Lombok 对这种字段生成 `isBorrowing()`，
Jackson 按 JavaBean 规则**去掉 `is` 前缀**，序列化出的字段名是 **`borrowing`**，而不是 `isBorrowing`。
前端读的是 `detail.isBorrowing`，永远取不到值 → 该提示块从未渲染。前端改用 `detail.borrowing`。

### 18.2 借用浏览导出五列为空

**现象**：导出的 CSV/XLSX 中，「目的分类 / 计划开始 / 计划归还 / 逾期天数 / 创建时间」全为空，
实验室管理员与系统管理员账号同样如此（与角色无关）。

**根因**：导出 SQL 用了 `borrow_record.*`，JDBC **按数据库原始列名返回**（`start_time`、`end_time`、
`overdue_days`、`create_time`、`purpose_category`），而写 CSV/XLSX 时读的是**驼峰键**
（`r.get("startTime")` 等）。单字段列（`purpose`、`reason`）恰好同名所以正常，
带下划线的列全部读不到。凡是被显式 `AS` 起过别名的列（`pickupTime`、`realReturnTime`、
`damageReport`、审批人/时间子查询）都正常，正好印证这一点。

**处理**：在 SQL 里给这五列显式 `AS` 别名。已实测导出第 1 行这五列由空变为有值。

### 18.3 统计口径：借用次数 vs 借用天数

原「借用次数」的口径是**借用记录条数**——一次借出即 1 次，与借了几天无关
（`COUNT(*)`，见 `/statistics/overview` 的 `borrowStats.total`）。

按要求新增两个指标：

| 指标 | 口径 |
| --- | --- |
| 累计借用天数 | 已归还按「实际借出 → 实际归还」，未归还按「计划开始 → 应归还」，**分钟精度**累计后折天 |
| 折合人时数 | 借用天数 × 8（约定 1 天 = 8 小时） |

> 首版用过 `DATEDIFF` + 「不足 1 天按 1 天」，实测发现问题：`DATEDIFF` 只取整天，
> 当天借还的记录会被算成 0 天；而强行按 1 天兜底又会把「21 秒借还」这种记录记成 1 天（8 人时），
> 严重虚高。改为分钟精度累加后折算，短时借用按比例计入。

### 18.4 统计范围：教师只能看名下设备

**根因**：`getCustodianForScope()` 的分支顺序有问题——

```java
if ("personal".equals(scope)) return user.getRealName();
if ("global".equals(scope)) return null;   // ← 在教师判断之前
if (userType == 1) return user.getRealName();   // ← 永远到不了
```

`global` 分支排在教师判断**之前**，因此教师只要传 `scope=global`（前端切换即可）就能拿到全院数据。

**处理**：按用户类型先分流——教师一律返回 `realName`（忽略 `global`），
实验室管理员/系统管理员才可全局（也可显式请求 `personal`）。
前端对教师**隐藏「全局/个人」切换**，避免给出一个切了也没用的入口。

> 权限框架整体未重构：本次只修「统计范围」这一处越权，改动局限在
> `StatisticsController.getCustodianForScope` 一个方法内。

### 18.5 验证

后端 `javac` 全量编译通过；手动 JUnit **231 通过 / 0 失败**；前端 `npm run build` 通过。
线上实测：导出五列有值、`borrowDays`/`personHours` 返回 6286.1 / 50289、教师请求 `scope=global` 返回其名下设备口径。

## 20. V3.0 终审页补初审信息、默认审批人修复、审计日志降噪（2026-09-29）

1. 后端 `cancelBorrow()` 只允许**本人**取消（`record.getUserId().equals(userId)`），
   而「借用浏览」是管理员页面，管理员一点就抛 `只能取消自己的借用申请`；
2. 前端写的是 `try{...}catch{}`——**空 catch 把确认框的「取消」和后端报错一起吞了**，
   所以界面上既没有成功提示也没有失败提示，表现为「点了没反应」。

**处理**：后端允许实验室管理员/系统管理员取消（与页面按钮可见性一致）；
前端把「确认框取消」与「业务失败」拆成两段 try，失败时弹出后端返回的原因。

### 21.5 卡片「借用中 564」与按该状态筛选的 24 条对不上

**根因**：两处口径不同——

| 位置 | 口径 |
| --- | --- |
| `/statistics/overview` 的 `borrowStats.borrowing` | `BORROWING 且未到期` **再加上全部 `OVERDUE`** |
| 借用浏览的状态筛选 | `status = 'BORROWING'` |

于是卡片把逾期也算进「借用中」，与筛选结果自然差出逾期的数量。

**处理**：统一为按 `status` 列计数——「借用中」= `BORROWING`，「逾期」= `OVERDUE`，
两者互斥且各自与筛选结果一致。状态列的实时性由 §17.2 的每小时任务保证。

### 20.8 设备默认审批人显示成具体账号（补）

§20.5 只改了**下拉选项**，**列表展示**与**借用申请页**仍在显示具体姓名（如「测试管理员2」）。
